Memo Pipeline Anatomy

How an Investment Memo (Late-Stage) run actually executes — every agent it spawns, what each one reads, how the document is assembled, and where the 30+ minutes and ~$15 go. Grounded in the code and in seven recorded runs on disk.

Overview

The run at a glance

Every agent is a claude -p CLI subprocess spawned by Python (never the API SDK), streaming JSON events back to the server. The pipeline is a chain of hard barriers: each phase must fully finish before the next starts. Only two phases run anything in parallel.

Prep Bootstrap Pure Python: resolve the company in companies.yaml, scope-check the stage via deterministic rules, mint the run folder, create the report record. No AI at run time — the company profile itself was typically AI-researched earlier, when the company was first added via deep search. seconds · $0
▼ barrier
Phase 2 8 parallel analysis passes Independent narrow agents (pressure tests, time-base, growth bridge, adoption, GTM, replacement, competitive, disconfirming). 4 workers → two waves. Each returns schema-validated JSON; Python writes the markdown. 5–11 min · ~$4–5
▼ barrier — synthesis reads all 8 outputs
Phase 3 English synthesis — the bottleneck One monolithic agent reads the 8 JSON outputs and writes the entire memo as one JSON package (~80K output tokens, 10–18 min per attempt). Validation gates can force up to 3 attempts; a cheaper “surgical repair” agent patches small defects instead. 19–52 min · $3.5–8/attempt
▼ barrier
Phase 4 Chinese fill The package is split into ~6–8 units (envelope + one per section) translated in parallel, then merged. The merge is one-way: translation can never alter the English. 6–8 min · ~$2–3
▼ barrier
Phase 5 Deterministic render + gates Pure Python turns the package into both DOCX files, in section order, with validation reports. Chinese-parity and English-quality gates run here — as warnings, never blockers. 0.6 s · $0

Two facts frame every optimization conversation

① The memo never exists as a document until the final half-second — it lives as one JSON “package” that a deterministic Python renderer turns into DOCX. Agents write data; Python writes files. ② Every one of the ~18 subprocesses — including the 8 pure-translation units — runs on the same top-tier model (claude-opus-5[1m]). There is no --model flag anywhere in the repo.

Phase 2

The eight analysis passes

Defined in memo_analysis.py:249-332, run on a thread pool capped at 4 workers (BSH_MEMO_FAST_MAX_WORKERS), so the 8 passes execute in two waves. They are genuinely independent: every pass receives identical inputs, none reads another's output, and their prompts differ only in a one-paragraph focus string. There is no per-pass skill file — one shared inline template in claude_runner.py:3705-3805 drives all eight. The big 112 KB memo skill is not used by the fast pipeline at all (legacy path only).

growth_bridgeWhat has to be true to get from today's revenue to the projectiongrowth_bridge.md

Output contract: each pass must return one JSON object (schema-enforced by the CLI's --json-schema): summary, ≤8 key findings with confidence levels, ≤8 supporting-evidence items, ≤6 disconfirming items, ≤5 evidence limits, ≤6 investment implications. Brevity is framed as a correctness requirement. Python renders the markdown from that JSON — the agent writes no files.

Failure semantics: passes get one attempt, no retries (15-min hard timeout, 3-min silence guard). A failed pass writes a “Pass failed — treat as explicit evidence gap” stub; the run only dies if all eight fail. Each pass's JSON records its own duration_ms, cost_usd, and full token usage — observed $0.30–$1.78 per pass.

Skip path: if an approved Memo Studio packet exists for the company, Phase 2 is skipped entirely and the packet becomes the synthesis input — the fastest configuration the pipeline has.

Phase 3

English synthesis — one giant call, heavily policed

One agent (run_memo_fast_english_package) reads analysis/fast/*.json as its primary input — the pass outputs are not pasted into the prompt; the agent is handed directory paths and told to read them. What is inlined: the company's registry entry as YAML, and four hard-coded contracts — voice (exec sell-side language rules), sources, block format, the 17 required memo components, and the risk-register format (the 5-row cards including our new Likelihood row).

It returns a single JSON object with two halves: seven synthesis artifacts (claim register, countercase, downside scenario, scenario swim lanes, source treatment, risk sensitivities, content coverage — these are written here, not in Phase 2) and the memo package — five fixed sections (executive_summary company_overview investment_highlights investment_risk financial_forecast_valuation) each built from typed blocks (heading / paragraph / bullets / callout / table), every string bilingual with zh deliberately left blank.

The gate gauntlet (per attempt, in order)

  1. Deterministic auto-repair — pure Python fixes known shape drift (key synonyms, missing IDs, prose-in-title) before judging.
  2. Structural validation — schema, 5 required sections, per-section content floors, 17 required components, non-empty sources, and the risk-card format gate (5 labeled rows, High|Medium|Low: likelihood, N/10 rating, cards ordered by rating).
  3. Pre-render quality lint — the package is rendered to a throwaway DOCX and linted: source-ID leaks outside Section VI, internal artifact names, ~90 sell-side voice violations, em-dash bridges, disclosure gaps without a stated treatment.
  4. Surgical repair — quality findings first go to a cheap patch agent (“same package, only the listed defects fixed”, ~2–8 min). Accepted only if both gates re-pass clean.
  5. Full regeneration — structural failures, or quality findings surgical repair couldn't clear, regenerate the entire package with the cumulative error list fed back. Up to 3 attempts; on the last attempt residual quality findings downgrade to warnings so the memo still ships.
Why this phase dominates

Each attempt is ~80K output tokens in one 10–18 minute uninterruptible generation at $3.50–8. The 40–60-minute runs on record were exactly these retries. The surgical-repair change (shipped 2026-08-21) is what cut the typical run from ~45–60 min to ~31–36 min. A parallel-English variant (spine + 5 section writers) exists behind BSH_MEMO_ENGLISH_PARALLEL but is off by default: the live NVIDIA validation run showed no wall-clock win at ~5× cost per attempt (66 min, $60.87) because the spine call alone takes ~9 minutes and the dominant failures were envelope strings the selective retry can't scope.

Phase 4–5

Chinese fill, then a half-second of rendering

Chinese: the English package is split into an envelope unit plus one unit per section; each unit is a pure-translation agent with pinned terminology (Likelihood→可能性, High/Medium/Low→高/中/低, ratings untouched). Units run 4-wide in parallel — this fan-out shipped earlier and did pay off, unlike the English one. The merge only copies a translation in when the English matches exactly and the slot is still blank, so translation can never corrupt the English. Any unit failure falls back to one monolithic translation call.

Render: Python applies a ~112-pattern deterministic voice cleanup to every English string, then memo_docx_renderer builds both DOCX files: cover page, TOC, sections strictly in package order with auto-numbered titles (I.–V.), risk cards as shaded key-value tables, and an appended “VI. Sources, Source Classes, and Fact Reference Index”. Claude is structurally banned from writing any renderer script — the run fails if one appears in the folder. Total render time: 0.6 seconds. There is nothing to optimize here.

Post-render gates are warnings, not blockers: the Chinese-parity gate (section shape/count/CJK checks) and the English quality lint both write reports and mark the run complete_with_warnings at worst. Resume is smart about this now: a Chinese-parity-only warning no longer triggers a 30-minute English regeneration.

Sources

What the agents actually read — and the web problem

Four input classes, in every pass's prompt:

InputOn diskHow it reaches the agent
Company registry entrydata/companies.yamlInlined as YAML — the only content pasted into prompts
Analyst backgrounddata/settings/serena_background.mdPath only; agent must choose to read it
Research corpusdata/research/<slug>/Directory access + a filename listing (capped at 80 names); agent reads what it wants
Memo Studio packet optionaldata/serena_analysis/<slug>/Directory access + listing, only when approved

The Document Library (data/uploads/) is deliberately excluded. The “Use in report” toggle in the Files tab isn't a flag — it physically moves the file between the two stores. Folder membership is the filter; there is no selection, excerpting, token budgeting, or dedup inside the corpus (a re-uploaded identical file is stored twice — its SHA-256 is computed but never compared).

Web retrieval is uncontrolled — confirmed

No memo agent is ever granted WebSearch/WebFetch in --allowedTools — but every agent runs with --permission-mode bypassPermissions, so the allowlist doesn't actually bind. The fast-pass prompts say nothing about the web either way, so each pass decides on its own. Real run logs show the result: 121, 58, 52, 14, 0, 0 web calls across six runs — in one run only 2 of 8 passes searched the web while the other 6 abstained. Nothing anywhere records whether a cited fact came from the corpus or the live web; every gate checks citation format, never origin. This is the root cause of the mixed provenance labels.

Citation model: memo body (Sections I–V) may use only source-class language (“company-reported”, “public third-party”); bracketed source IDs are legal solely in Section VI. The lint enforces this at P0. The sources[] array requires id / title / class / treatment / as-of per entry — but class is free text, unconnected to the 7 canonical source classes the document store uses.

Levers

Where optimization is actually available

Model tiering — the untouched cost lever

Everything runs on claude-opus-5[1m]: the 8 narrow schema-bounded passes, and — hardest to justify — the 8 pure-translation Chinese units. A --model parameter doesn't exist in the code. Routing translation (and possibly some passes) to a cheaper model is the largest cost cut available, likely with a latency side-benefit, and it's a small code change. The risk to manage: pass quality feeds synthesis quality feeds retry count.

Keep synthesis to one attempt — retries are the whole story

The spread between a 31-minute and a 56-minute run is purely synthesis attempts. The winning pattern so far has been making the first attempt pass: surgical repair, cumulative validation feedback, and writer/validator alignment (the disclosure gate went from striking 3-of-3 runs to zero). Continuing that — auditing what still triggers regenerations and aligning the prompt contract with each gate — is cheaper than any architectural change.

Analysis workers 4 → 8

8 passes over 4 workers means two waves; the slowest pass gates each wave. Setting BSH_MEMO_FAST_MAX_WORKERS=8 collapses Phase 2 to one wave — plausibly 3–5 minutes off a run for a config change. (Note: .env.example already claims 8 is the default; the code default is actually 4. The docs' own timing-calibration task for this comparison was never run.)

Memo Studio packet mode — skip Phase 2 entirely

An approved studio packet already bypasses all 8 analysis subprocesses. This is the fastest existing path and it's exactly the memo-run→studio bridge on our roadmap: the more analysis happens interactively before the run, the less the run has to do.

Decide the web policy — quality lever, not latency

Either grant web tools explicitly with prompt rules about when to search and how to label web-sourced facts, or forbid them and run corpus-only. Today's silent nondeterminism (0–121 web calls per run) makes provenance unauditable. Also worth recording source origin per fact so the gates can check it.

Restructuring the English monolith — approach with evidence

The obvious move (parallel per-section writers) was built, measured, and rejected: no wall-clock win at 5× cost. The flag stays for future tuning (a lighter spine, envelope-scoped repair). Before re-attempting, the cheaper experiments are shrinking the package the model must emit and pruning what the synthesis prompt asks for.

Findings

Loose ends the investigation surfaced

  • docs/memo-pipeline.md is stale — it omits data/research/ entirely and lists the “use in report” toggle as planned but not built, though both shipped. docs/architecture.md is the accurate one.
  • The analyst background never reaches the memo's actual author. The Phase 3 synthesis prompt (and the parallel section writers) are granted read access to serena_background.md but never told it exists; voice comes from a hard-coded contract duplicating its content in Python. Only the 8 analysis passes are pointed at the file.
  • The prompt promises a translation block in the registry entry that doesn't exist in companies.yaml — all Chinese comes from the translation pass.
  • .env.example defaults disagree with the code (workers 8 vs 4, retries 1 vs 2, backoff 20s vs 0s). The code defaults are live.
  • Resume silently drops binary sources: a resumed run's allowed-read list excludes PDFs/DOCX/images from the corpus, so it can cite fewer sources than the original run.
  • Cancel doesn't cancel: the termination hook for in-flight passes exists but nothing consumes it — a user cancel lets running subprocesses finish (and bill).
