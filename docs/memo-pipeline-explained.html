How a memo gets written

The investment-memo pipeline, end to end — what runs, in what order, and which file tells each agent what to do.

BSH Research Center · updated 2026-09-20 · numbers from the Surge AI run 2026-09-20__070546

The one-paragraph version. A memo is not written by one model call. It is written by about twenty agents working in five phases. Python never writes a sentence of the memo — it decides who runs, in what order, what each one is allowed to see, and whether the result is good enough to keep. The editorial judgment lives in Markdown files under skills/memo/, which non-engineers edit. The result is two Word documents, English and Chinese, around 20,000 words each.

That run: 14 minutes 27 seconds, $18.33, 22,000 words in two languages. Phases 3 and 4 are roughly two-thirds of the clock and most of the money.

Phase 1 — Intake

Cheap and mostly deterministic. Three questions get answered before any research starts, because the answers decide which instructions everyone else reads.

QuestionHow it is answeredWhat it changes
What stage is this company?From the funding round in the registry — seed → early, series f → late. No signal means late by default.Which structure profile is loaded, and the scorecard weights.
What kind of company is it?The registry's vertical field if set. Otherwise one small model call with no tools, which must return one of six types.Adds a "company type lens" to every later prompt, and can override the scorecard weights.
Which report shape?The user picks full or compact in the UI.Compact = 7 sections, ~20k words. Full = 12 sections.

A seed-stage AI-infrastructure company and a late-stage AI-application company get different section lists, different scoring weights, and different research emphasis — all from these three answers.

Phase 2 — Eight researchers

Eight agents launch at the same time. Each gets one job, one question, and writes exactly one file into analysis/. None of them can see each other's work. They are researchers, not writers — nothing they produce reaches the reader directly.

PassThe question it answersWrites
numbers_integrityDo the numbers agree with each other, and what period is each one from?numbers_integrity.md
growth_bridgeWhere did the growth actually come from?growth_bridge.md
valuation_exitWhat is it worth, and how would we ever get out?valuation_and_exit.md
market_sizingHow big is the market — by every published estimate, not just one?market_sizing.md
competitive_positionWho else is in this fight, and who is winning?competitive_position.md
adoption_distributionAre customers actually using it, and how does it reach them?adoption_and_distribution.md
team_governanceWho runs it, what have they done before, who controls it?team_governance.md
alternative_explanationsArgue against the investment. What else explains these numbers?disconfirming_evidence.md
Why eight and not twelve. There used to be twelve. Every pass fills whatever limit it is given, so twelve passes handed the writers more than three hundred findings to write a 3,500-word memo from — and the writing phase is the expensive one. Passes that read the same evidence were merged, so one agent forms one judgment from one reading instead of two agents splitting it. Passes that read different evidence, or whose job is to disagree, stayed separate. alternative_explanations survives precisely because its job is to argue with the others.

Phase 3 — The spine, then the writers

This is the part worth understanding, because it is where most of the engineering is.

Step one: fix the facts (the "spine")

One agent reads all eight research files and produces no prose at all. It produces a set of pins: the facts every section must agree on.

  • The recommendation sentence, word for word.
  • A scorecard: nine dimensions, each scored out of its own weight, with the reason and the evidence.
  • Three investment highlights, each tied to a scorecard dimension.
  • The risks, each with an area, a rating, a likelihood and a plain-words impact.
  • The calculation notes (C1, C2…) — the arithmetic behind every derived number.
  • The fair value range, the entry price, the company's stage.

The spine is the answer to a real problem: seven writers working in parallel will otherwise each invent their own valuation, their own verdict, and their own version of the growth rate. Pinning happens once, before any of them start.

Step two: seven writers, at once

Each section gets its own agent. Each agent receives the same shared context plus its own section contract:

shared by every writer (cached, byte-identical) per writer ──────────────────────────────────────────────── ────────────────────────── voice_contract.md how the memo is allowed its own `## section:` block to speak from the structure profile structure_addendum.md citations, charts, honesty, the pinned facts it must "teach, don't assert" echo word for word types/<type>.md where the case usually lives its word budget for this kind of company (1,400–2,800 words)

Step three: one section is still too big for one answer

A 2,600-word section with three subsections is more than a model reliably returns in a single structured reply. So a section is not one call. It is one call per subsection, run in order, each one seeing what came before.

This was the single biggest reliability fix in the project, and it landed differently on the two engines — see below.

Phase 4 — Chinese

Every piece of text in the memo is a pair: {en, zh}. The English is written first and the Chinese has to catch up. Two mechanisms do it.

The chase (speculative)

The moment a section is finished, a translator agent starts on it — while the other sections are still being written. By the time the package is assembled, most of the translation is already done.

Translations are adopted only where the English still matches exactly and the citation markers line up. A stale translation is dropped, never merged.

The gap fill (serial)

Whatever the chase missed gets translated at the end, in one pass. This is the slow path, so the chase exists to keep it small.

On the Surge AI run: 624 strings adopted from the chase, 24 left for the gap fill.

Phase 5 — Render and check

No model calls here. Python builds both .docx files with python-docx in about half a second, then runs the gates.

The gates — five layers, each catching something different

This is the part that makes the output usable rather than merely produced. Each layer exists because something specific went wrong in a real run.

GateWhenWhat it catchesCost of failing
Spine pin gateAfter the spine, before any writer startsArithmetic that does not add up; a scorecard that contradicts the verdict; a stage that does not match the classification; a pinned sentence containing a phrase the voice gate will later ban.One cheap spine retry.
Structural repairBefore validationShapes the model chose that we did not ask for — a table that named its own columns, a chart delivered as a flat list, a field under a different name. Repairs are deterministic and lossless.Nothing. This layer exists to avoid failures.
Renderer validationOn the assembled packageMissing sections, missing required components, word budgets blown, malformed blocks.A regeneration round, or a targeted trim.
Pin echo checkOn the assembled packageA writer quietly changed a pinned fact. Every pin must appear verbatim where it was promised.Reported; repaired surgically.
Quality lint + Chinese parityOn the finished .docxBanned voice ("the memo shows…", advice instead of a recommendation), and any English left sitting in a Chinese slot.Warnings on the delivered report.
A gate can be wrong, and that is expensive. If a rule fires on correct prose, no repair agent can fix it — there is nothing to fix — so the run burns every attempt it has. A memo for an enterprise document search company tripped the rule that bans "the document" (meaning "this memo"). Another lost two attempts to "a named institutional lead" — a phrase banned as a diligence checklist item, which is also the plainest way to name the one thing that would change the call. Both rules were right in general and wrong for that company. Both are now scoped.

The skills folder — where the judgment lives

Every editorial instruction is a Markdown file, not Python. The English files are what agents read. The Chinese twins under zh/ are what the investment team edits. A script checks the two never drift apart.

Why this matters. The people who know what a good memo looks like are not the people who can edit Python. Moving the prompts into files with Chinese twins means the investment team can change the memo's voice, structure and emphasis without a developer — and the test suite still fails if an English file changes without its Chinese twin being re-synced.

Two engines, one pipeline

The same pipeline runs on Claude or on Gemini. The interesting difference was not model quality. It was how many calls a unit of writing is spread across.

Claude

Runs as a local subprocess with a filesystem. A section writer writes each subsection to its own file and returns a short receipt. The server assembles the files. Content never travels through the reply, so nothing is lost to a truncated response.

sections arrive English-only → the Chinese chase does real work (624 strings adopted).

Gemini

Runs over an API with no filesystem. A section used to be one reply — all or nothing, and a long one failed as a unit. Now it is one API call per subsection, assembled identically.

sections arrive already bilingual → most chases are skipped as unnecessary.

Mechanical defects on the first attempt fell from 360 → 39 → 4 across three rounds of this work. The lesson generalises: when a structured reply is unreliable, the fix is usually to split the ask, not to enlarge the limit.

Three bugs that keep coming back

Worth naming, because they have each appeared a dozen times in different clothes.

1. One fact, written in two places, drifting apart

The length gate counted words one way and the renderer counted them another, so sections passed the gate and failed the package. The prompt said one thing and the validator checked another. The profile's stage said "late" while the scorecard used early weights. Every instance looks different; every fix is the same — make one of them ask the other.

2. Presence checked, validity never asked

A component counted as "present" because a block declared its name — even when the block was empty. A translation slot counted as "filled" because it was not blank — even when it held English. The question "is it there?" is not the question "is it right?".

3. Two gates demanding opposite things

The echo gate required a pinned sentence word for word. The voice gate banned a phrase inside that sentence. No writer could satisfy both, so three attempts and three repairs all failed and the memo shipped with the finding anyway. The fix was to check the sentence where it is written, not where it is copied.
