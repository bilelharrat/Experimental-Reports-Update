一份备忘录是怎么写出来的

投资备忘录生成管线的全过程——什么在跑、按什么顺序跑、每个 Agent 的指令来自哪个文件。

BSH Research Center · 更新于 2026-09-20 · 数据取自 Surge AI 运行 2026-09-20__070546

一段话版本。一份备忘录不是一次模型调用写出来的，而是大约二十个 Agent 分五个阶段协作完成的。Python 一个字都不写——它只负责决定谁来跑、按什么顺序跑、每个 Agent 能看到什么，以及产出是否合格。编辑判断全部存放在 skills/memo/ 下的 Markdown 文件里，非工程师也能直接改。最终产出是两份 Word 文档，中英各一份，每份约两万字。

阶段 1 —— 接入

便宜，且基本是确定性的。在任何研究开始之前，先回答三个问题，因为这三个答案决定了后面所有人读到的指令。

问题怎么回答它影响什么
公司处于什么阶段？取自档案中的融资轮次——seed → 早期，series f → 后期。没有明确信号则默认按后期处理。加载哪一套结构配置，以及评分卡的权重。
这是一家什么类型的公司？优先用档案里的 vertical 字段；没有则跑一次不带任何工具的小模型调用，必须从六个类型中返回一个。给后续所有提示词追加一层"公司类型透镜"，并可覆盖评分卡权重。
写哪种报告？用户在界面上选完整版还是精简版。精简版 = 7 个章节，约 2 万字；完整版 = 12 个章节。

一家种子期的 AI 基础设施公司，和一家后期的 AI 应用公司，会得到不同的章节清单、不同的评分权重、不同的研究侧重——全部由这三个答案推导出来。

阶段 2 —— 八个研究员

八个 Agent 同时启动。每个只领一项任务、只回答一个问题，并且只写出一个文件到 analysis/ 目录。它们互相看不到对方的成果。它们是研究员，不是写作者——它们的产出不会直接出现在读者面前。

通道它回答的问题产出文件
numbers_integrity各项数字彼此是否自洽？每个数字对应的是哪个时间口径？numbers_integrity.md
growth_bridge增长究竟从哪里来的？growth_bridge.md
valuation_exit它值多少钱？我们将来怎么退出？valuation_and_exit.md
market_sizing市场有多大——要列出每一个公开估算，而不是只取一个。market_sizing.md
competitive_position这条赛道上还有谁？谁在赢？competitive_position.md
adoption_distribution客户是真的在用吗？产品怎么触达他们？adoption_and_distribution.md
team_governance谁在经营？他们此前做成过什么？控制权在谁手里？team_governance.md
alternative_explanations专门唱反调。这些数字还有没有别的解释？disconfirming_evidence.md
为什么是八个，而不是十二个。原本是十二个。每个通道都会把给它的产出上限填满，于是十二个通道给写作阶段塞了三百多条发现，而要写的只是一份三千五百词的备忘录——偏偏写作阶段才是最贵的。于是把读同一批证据的通道合并：让一个 Agent 读一遍、形成一个判断，而不是两个 Agent 把同一个判断拆成两半。读不同证据的、以及职责就是唱反调的通道，保持独立。alternative_explanations 能活下来，正是因为它的任务就是和其他人争论。

阶段 3 —— 先钉事实，再写正文

这是最值得理解的一段，因为大部分工程复杂度都在这里。

第一步：钉死事实（"主干"）

一个 Agent 读完全部八份研究文件，然后一句正文都不写。它产出的是一组钉子：所有章节都必须遵守的事实。

  • 投资建议句，一字不差。
  • 一张评分卡：九个维度，各自按权重打分，并附理由与证据。
  • 三条投资亮点，每条挂靠到一个评分维度。
  • 风险清单，每条带领域、评分、可能性，以及一句大白话的影响描述。
  • 计算备注（C1、C2……）——每一个推导出来的数字背后的算式。
  • 合理估值区间、入场价格、公司阶段。

主干要解决的是一个真实问题：七个并行的写作者，否则会各自编出自己的估值、自己的结论、自己版本的增长率。所以"钉事实"只做一次，且在所有人动笔之前完成。

第二步：七个写作者，同时开工

每个章节配一个 Agent。每个 Agent 拿到的是同一份共享上下文，外加它自己的章节契约：

所有写作者共享（带缓存，逐字节一致） 每个写作者各自专属 ────────────────────────────────────── ────────────────────────── voice_contract.md 备忘录允许怎么说话 结构配置里属于它的 `## section:` 区块 structure_addendum.md 引用、图表、数据诚实、 它必须逐字复述的 "讲清楚，别断言" 那些钉死的事实 types/<type>.md 这类公司的投资逻辑 它的字数预算 通常落在哪里 （1,400–2,800 字）

第三步：一个章节对一次回答来说还是太大

一个 2,600 词、含三个子章节的章节，超出了模型在单次结构化回复中能稳定返回的范围。所以一个章节不是一次调用，而是每个子章节一次调用，顺序执行，后一次能看到前面已经写好的内容。

这是整个项目里最关键的一次可靠性改造，而它在两个引擎上的落地方式并不相同——见下文。

阶段 4 —— 中文

备忘录里的每一段文本都是一对 {en, zh}。英文先写，中文得追上来。靠两套机制完成。

预翻译（投机式）

某个章节一写完，翻译 Agent 立刻开始翻它——此时其他章节还在写。等到组装成包的时候，大部分翻译已经就绪。

只有在英文原文完全一致、且引用标记对得上的前提下，译文才会被采纳。过期的译文一律丢弃，绝不合并。

补漏（串行）

预翻译没覆盖到的，在最后统一翻一遍。这是慢路径，所以预翻译存在的意义就是把它压到最小。

Surge AI 那次运行：预翻译采纳 624 条，只剩 24 条交给补漏。

阶段 5 —— 渲染与核查

这一步没有任何模型调用。Python 用 python-docx 在约半秒内生成两份 .docx，然后跑各道关卡。

关卡 —— 五层，各拦各的

正是这部分让产出"可用"，而不只是"生成出来了"。每一层的存在，都对应着某次真实运行中出过的具体问题。

关卡时机拦截什么失败代价
主干钉子校验主干产出后、任何写作者启动之前算不平的算术；与结论自相矛盾的评分卡；与分类不符的公司阶段；以及钉死的句子里含有后续语气关卡会禁用的措辞。重跑一次便宜的主干。
结构修复校验之前模型自选的、我们没要求的形态——自带列名的表格、被拍平成列表的图表、换了名字的字段。所有修复都是确定性且无损的。没有代价。这一层的存在就是为了避免失败。
渲染器校验在组装好的包上缺章节、缺必备组件、字数超预算、区块格式非法。重新生成一轮，或做一次定向删减。
钉子复述校验在组装好的包上某个写作者偷偷改了钉死的事实。每颗钉子都必须一字不差地出现在承诺的位置。记录并做外科式修复。
质量语气检查 + 中英一致性在成品 .docx 上被禁用的语气（"本备忘录显示……"、把建议写成劝告），以及任何残留在中文位置上的英文。在交付的报告上标记为警告。
关卡也可能判错，而且代价不小。如果某条规则命中的是本来就正确的句子，修复 Agent 无从下手——因为根本没有可改的东西——于是整次运行会把所有重试次数耗光。一份写企业文档搜索公司的备忘录，触发了禁用"the document"（本意是指"本备忘录"）的规则。另一份为"a named institutional lead"（具名领投机构）连丢两次尝试——这个措辞被当作尽调清单用语禁用，可它恰恰是描述"什么会改变我们判断"最朴素的说法。两条规则在一般情况下都对，在那两家公司身上都错。现在都已经收窄了适用范围。

skills 目录 —— 判断力存放的地方

所有编辑指令都是 Markdown 文件，而不是 Python。英文文件是 Agent 实际读取的版本；zh/ 下的中文孪生文件，是投资团队实际编辑的版本。有脚本保证两者不会失同步。

这样做的意义。知道什么才算一份好备忘录的人，往往不是能改 Python 的人。把提示词搬进带中文孪生的文件之后，投资团队不需要工程师就能调整备忘录的语气、结构与侧重——同时，只要英文文件改动后中文孪生没有重新同步，测试就会失败。

两个引擎，同一条管线

同一条管线既能跑 Claude 也能跑 Gemini。真正有意思的差别不在模型能力，而在一个写作单元被摊到多少次调用上。

Claude

以本地子进程运行，有文件系统。章节写作者把每个子章节各写进一个文件，只返回一张简短的回执。由服务端负责拼装。正文从不经过回复体，因此不会因为回复被截断而丢内容。

章节只带英文 → 中文预翻译真正有活干（采纳 624 条）。

Gemini

走 API，没有文件系统。过去一个章节就是一次回复——要么全有要么全无，篇幅一长就整体失败。现在改成每个子章节一次 API 调用，拼装方式完全相同。

章节直接是中英双语 → 大部分预翻译被判定为不必要而跳过。

首次尝试的机械性缺陷，在三轮改造中从 360 → 39 → 4。这个经验可以推广：当结构化回复不稳定时，正确的解法通常是拆要求，而不是调大上限。

反复出现的三类 Bug

值得单独命名，因为它们各自已经换着马甲出现过十几次。

1. 同一个事实写在两处，然后各自漂移

字数关卡按一种方式数词，渲染器按另一种方式数，于是章节过了关卡却挂在打包上。提示词说的是一套，校验器查的是另一套。配置里的阶段写着"后期"，评分卡却用的是早期权重。每一次表现都不一样；每一次的解法都一样——让其中一处去问另一处。

2. 只检查"在不在"，从不问"对不对"

一个组件只要区块声明了它的名字就算"存在"——哪怕那个区块是空的。一个翻译槽位只要不是空白就算"已填"——哪怕里面装的是英文。"它在吗？"和"它对吗？"从来不是同一个问题。

3. 两道关卡要求互相矛盾

复述关卡要求钉死的句子一字不差，语气关卡却禁用了这句话里的某个措辞。没有任何写作者能同时满足两者，于是三次尝试、三次修复全部失败，备忘录最终还是带着这条问题交付了。解法是：在句子被写出来的地方就检查它，而不是在它被复制到的地方。
