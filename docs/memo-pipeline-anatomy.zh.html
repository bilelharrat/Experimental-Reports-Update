总览

一次运行的全貌

每个 Agent 都是由 Python 启动的 claude -p 命令行子进程（从不走 API SDK），以 JSON 事件流的方式向服务端回报进度。整条管线是一串硬性屏障：每个阶段必须完全结束，下一阶段才能开始。全程只有两个阶段存在并行。

准备阶段 初始化 纯 Python：在 companies.yaml 中解析公司、用确定性规则校验投资阶段是否符合范围、创建运行目录、建立报告记录。运行时不涉及 AI——但公司档案本身通常是更早添加公司时由 AI 深度搜索生成的。 数秒 · $0

两条事实框定所有优化讨论

① 备忘录在最后那半秒之前从未以「文档」形态存在——它一直是一个 JSON「包」，由确定性的 Python 渲染器转成 DOCX。Agent 只产出数据，文件由 Python 写。② 全部约 18 个子进程——包括 8 个纯翻译单元——运行在同一个顶级模型（claude-opus-5[1m]）上。整个仓库里不存在 --model 参数。

阶段 2

八条分析通道

定义在 memo_analysis.py:249-332，在上限为 4 个工作线程的线程池上运行（BSH_MEMO_FAST_MAX_WORKERS），因此 8 条通道分两批执行。它们是真正相互独立的：每条通道拿到完全相同的输入，谁也不读别人的输出，Prompt 之间只差一段「关注点」描述。不存在按通道划分的技能文件——claude_runner.py:3705-3805 里的一个共享内联模板驱动全部八条。那份 112 KB 的备忘录大技能文件在快速管线里完全不被使用（仅遗留路径使用）。

通道关注点产出文件
arithmetic_denominators对数字做压力测试、单位经济核算pressure_tests.md
time_base增长断言的时间窗口是否诚实time_base_checks.md
growth_bridge从当前收入到预测值之间必须成立什么growth_bridge.md

输出契约：每条通道必须返回一个 JSON 对象（由 CLI 的 --json-schema 强制校验）：摘要、≤8 条带置信度的关键发现、≤8 条支持性证据、≤6 条反证、≤5 条证据局限、≤6 条投资含义。「简洁」被定义为正确性要求的一部分。Markdown 由 Python 从该 JSON 渲染——Agent 不写任何文件。

失败语义：每条通道只有一次机会，不重试（15 分钟硬超时，3 分钟静默保护）。失败的通道会写入一个「通道失败——按明确的证据缺口处理」占位文件；只有八条全部失败才会终止整次运行。每条通道的 JSON 各自记录 duration_ms、cost_usd 和完整 token 用量——实测每条 $0.30–$1.78。

跳过路径：如果该公司存在已批准的 Memo Studio 分析包，阶段 2 会被整体跳过，分析包直接作为合成输入——这是当前管线里最快的配置。

阶段 3

英文合成——一次巨型调用，层层设卡

单个 Agent（run_memo_fast_english_package）以 analysis/fast/*.json 为主要输入——通道输出不会被粘贴进 Prompt，Agent 只拿到目录路径并被要求自行读取。真正内联进 Prompt 的是：公司注册表条目（YAML 格式），以及几份硬编码契约——行文语气（高管级卖方语言规范）、来源、区块格式、17 个必备备忘录组件，以及风险登记格式（含我们新加 Likelihood 行的五行风险卡）。

它返回单个 JSON 对象，分为两半：七份合成产物（声明登记、反方论证、下行情景、情景泳道、来源处理、风险敏感性、内容覆盖——这些是在这里写出的，不在阶段 2），以及备忘录包——五个固定章节（executive_summary company_overview investment_highlights investment_risk financial_forecast_valuation），每个章节由带类型的区块组成（标题 / 段落 / 列表 / 提示框 / 表格），所有字符串均为双语结构、zh 一栏刻意留空。

校验关卡（每次尝试按序执行）

  1. 确定性自动修复——纯 Python 先修掉已知的结构漂移（键名同义词、缺失 ID、标题里混入正文），再进入评判。
  2. 结构校验——Schema、5 个必备章节、各章节内容下限、17 个必备组件、来源非空，以及风险卡格式门（5 个带标签的行、High|Medium|Low: 格式的可能性、N/10 格式的评分、卡片按评分从高到低排列）。
  3. 渲染前质量检查——先把包渲染成一次性 DOCX 再做静态检查：来源 ID 泄漏到第 VI 章之外、内部工件名称外泄、约 90 条卖方语气违规、破折号桥接句、缺少处理说明的披露缺口。
  4. 外科手术式修复——质量问题先交给一个廉价的补丁 Agent（「同一个包，只修列出的缺陷」，约 2–8 分钟）。只有两道门重新全部通过才会被采纳。
  5. 整包重做——结构性失败、或手术修复清不掉的质量问题，会带着累积的错误清单重新生成整个包。最多 3 次尝试；最后一次尝试中残留的质量问题降级为警告，备忘录照常交付。
为什么这个阶段占大头

每次尝试都是约 8 万输出 token 的单次不可中断生成，耗时 10–18 分钟、花费 $3.50–8。历史上那些 40–60 分钟的运行正是这些重试造成的。「外科手术式修复」（2026-08-21 上线）正是把典型运行从约 45–60 分钟压到约 31–36 分钟的那次改动。并行英文变体（骨架 + 5 个章节写手）藏在 BSH_MEMO_ENGLISH_PARALLEL 开关后，默认关闭：NVIDIA 实测运行显示总耗时毫无优势、单次尝试成本约 5 倍（66 分钟，$60.87），因为仅骨架调用就要约 9 分钟，且主要失败出在选择性重试无法定位的信封字符串上。

阶段 4–5

中文填充，然后是半秒钟的渲染

中文：英文包被切分为一个信封单元加每章节一个单元；每个单元是一个纯翻译 Agent，术语被钉死（Likelihood→可能性、High/Medium/Low→高/中/低、评分原样保留）。单元以 4 路并行运行——这次拆分早已上线且确实见效，与英文那次不同。合并时只有当英文完全一致且中文槽位仍为空才会写入译文，因此翻译永远不可能污染英文。任何单元失败都会回退为一次整包翻译调用。

渲染：Python 先对所有英文字符串执行约 112 条规则的确定性语气清理，然后由 memo_docx_renderer 构建两份 DOCX：封面、目录、严格按包内顺序排列并自动编号的章节（I.–V.）、以底纹键值表呈现的风险卡，以及追加的「VI. 来源、来源类别与事实索引」。Claude 被结构性禁止编写任何渲染脚本——运行目录里一旦出现此类脚本，整次运行直接判失败。总渲染耗时：0.6 秒。这里没有任何可优化的空间。

渲染后的质量门只警告、不拦截：中英文对齐门（章节形态/数量/中文字符检查）和英文质量检查都会写出报告，最坏也只是把运行标记为 complete_with_warnings。续跑逻辑现在也变聪明了：仅有中英文对齐警告时，不会再触发 30 分钟的英文重做。

来源

Agent 究竟读了什么——以及联网检索问题

每条通道的 Prompt 中包含四类输入：

输入磁盘位置抵达 Agent 的方式
公司注册表条目data/companies.yaml以 YAML 内联——唯一被粘贴进 Prompt 的内容
分析师背景data/settings/serena_background.md仅给路径；是否读取由 Agent 自行决定
研究语料库data/research/<slug>/目录访问权 + 文件名列表（上限 80 个）；读什么由 Agent 自选
Memo Studio 分析包 可选data/serena_analysis/<slug>/目录访问权 + 文件列表，仅在已批准时提供

文档库（data/uploads/）被刻意排除在外。Files 页里的「用于报告」开关不是一个标记位——它会把文件在两个存储之间物理搬移。「在不在那个文件夹里」就是唯一的筛选条件；语料库内部没有任何挑选、摘录、token 预算或去重逻辑（重复上传同一文件会存两份——SHA-256 算了但从不比对）。

联网检索处于失控状态——已证实

没有任何备忘录 Agent 的 --allowedTools 里授予过 WebSearch/WebFetch——但所有 Agent 都运行在 --permission-mode bypassPermissions 之下，所以这份白名单实际上并不生效。快速通道的 Prompt 对联网只字未提，于是每条通道各自随意决定。真实运行日志给出的结果是：六次运行的联网调用次数分别为 121、58、52、14、0、0——其中一次运行里只有 8 条通道中的 2 条上网搜索，另外 6 条完全没碰。系统中没有任何地方记录某条引用事实到底来自语料库还是实时网络；所有质量门检查的都是引用格式，从不检查来源出处。这正是我们之前注意到的来源标签混乱的根因。

引用模型：备忘录正文（第 I–V 章）只允许使用来源类别语言（「公司披露」「公开第三方」）；方括号来源 ID 只允许出现在第 VI 章。质量检查以 P0 级别强制执行这条规则。sources[] 数组的每个条目要求 id / title / class / treatment / as-of 齐全——但 class 是自由文本，与文档存储所用的 7 个规范来源类别互不相通。

优化杠杆

优化空间到底在哪里

模型分级——尚未动用的成本杠杆

一切都跑在 claude-opus-5[1m] 上：8 条 Schema 约束的窄域通道，以及最说不过去的——8 个纯翻译中文单元。代码里根本不存在 --model 参数。把翻译（可能还有部分分析通道）改路由到更便宜的模型，是现成的最大成本削减项，很可能顺带缩短耗时，而且改动很小。需要管理的风险：通道质量影响合成质量，合成质量又影响重试次数。

让合成一次通过——重试就是全部的差距

31 分钟的运行和 56 分钟的运行之间，差的全是合成尝试次数。迄今的制胜模式是让第一次尝试就通过：外科手术式修复、累积式校验反馈、写手与校验器的对齐（披露缺口门从「三连中三」降到零命中）。沿着这条路继续——排查还有什么在触发整包重做、让 Prompt 契约与每道门对齐——比任何架构级改动都便宜。

分析并发 4 → 8

8 条通道配 4 个工作线程意味着分两批跑；每批都被最慢的那条通道拖住。设 BSH_MEMO_FAST_MAX_WORKERS=8 可把阶段 2 压成一批——一个配置改动大概能省 3–5 分钟。（注意：.env.example 声称默认值已是 8，代码里实际默认是 4。文档里那项对比测试的校准任务从未执行过。）

Memo Studio 分析包模式——整体跳过阶段 2

已批准的 Studio 分析包本来就能绕过全部 8 个分析子进程。这是现存最快的路径，而且正是我们路线图上「备忘录运行 → Studio」联动那一项：运行前交互式完成的分析越多，运行本身要做的就越少。

定下联网策略——这是质量杠杆，不是速度杠杆

要么显式授予联网工具，并在 Prompt 里写清什么时候搜索、联网来源的事实如何标注；要么明令禁止、只用语料库。现在这种无声的随机性（每次运行 0–121 次联网调用）让来源出处根本无法审计。同时值得给每条事实记录来源出处，让质量门能够核验。

重构英文巨型调用——务必用证据说话

最直觉的方案（按章节并行写作）已经被实现、实测并否决：总耗时没有优势，成本 5 倍。开关保留待未来调优（更轻的骨架、针对信封的定向修复）。在再次尝试之前，更便宜的实验是缩小模型必须产出的包体、以及精简合成 Prompt 的要求清单。

遗留问题

调查中发现的松动之处

  • docs/memo-pipeline.md 已过时——它完全没提 data/research/，并把「用于报告」开关列为已规划未实现，但两者都早已上线。docs/architecture.md 才是准确的那份。
  • 分析师背景从未真正抵达备忘录的执笔者。阶段 3 的合成 Prompt（以及并行章节写手）拥有 serena_background.md 的读取权限，却从未被告知这个文件的存在；行文语气来自 Python 里一份复述其内容的硬编码契约。只有 8 条分析通道被明确指向了该文件。
  • Prompt 承诺注册表条目里有一个 translation 区块，但它并不存在于 companies.yaml——所有中文都来自翻译通道。
  • .env.example 的默认值与代码不一致（并发 8 vs 4，重试 1 vs 2，退避 20 秒 vs 0 秒）。实际生效的是代码默认值。
  • 续跑会悄悄丢弃二进制来源：续跑的允许读取清单排除了语料库中的 PDF/DOCX/图片，因此续跑可能比原始运行引用更少的来源。
  • 取消并不能取消：终止进行中通道的钩子写了却没人消费——用户取消后，正在运行的子进程会继续跑完（并继续计费）。
